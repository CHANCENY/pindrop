Core

Logging

Pindrop's logger is PSR-3 compatible. It ships with three drivers — file, database, and null — switchable via .env. Context arrays are stored alongside each log entry for structured debugging.

Configuration

LOG_ENABLED=true
LOG_DRIVER=file            # file | database | null
LOG_FILE=[ROOT]/.logs/reports.log

Log Levels

LevelConstantWhen to use
emergencyLoggerInterface::EMERGENCYSystem is unusable
alertLoggerInterface::ALERTImmediate action required
criticalLoggerInterface::CRITICALCritical conditions
errorLoggerInterface::ERRORRuntime errors that don't require stopping execution
warningLoggerInterface::WARNINGExceptional occurrences that aren't errors
noticeLoggerInterface::NOTICENormal but significant events
infoLoggerInterface::INFOInteresting events — user logins, operations
debugLoggerInterface::DEBUGDetailed debug information

Using the Logger

$logger = getAppContainer()->get('logger');

// Basic
$logger->info('User logged in');
$logger->error('Payment failed');
$logger->warning('Deprecated method called');

// With context array (stored alongside the message)
$logger->info('Order placed', [
    'order_id' => 1234,
    'user_id'  => 42,
    'total'    => 99.99,
]);

$logger->error('Query failed', [
    'sql'   => $sql,
    'error' => $e->getMessage(),
    'trace' => $e->getTraceAsString(),
]);

// Generic level method
$logger->log('info', 'Something happened', ['key' => 'value']);

Injecting via Services

# services.yml
my_plugin.service:
  class: Simp\Pindrop\Modules\my_plugin\src\Services\MyService
  arguments:
    - "@database"
    - "@logger"
class MyService
{
    public function __construct(
        private DatabaseService $db,
        private LoggerInterface $logger
    ) {}

    public function doWork(): void
    {
        $this->logger->info('Starting work');
        try {
            // ...
            $this->logger->info('Work completed');
        } catch (\Exception $e) {
            $this->logger->error('Work failed', ['error' => $e->getMessage()]);
        }
    }
}

Log Drivers

File driver (default)

Writes to the path in LOG_FILE. Each entry is one line with timestamp, level, message, and JSON-encoded context. The file is protected by .htaccess in the .logs/ directory.

Database driver

Writes to a logs table. Set LOG_DRIVER=database. The table is created automatically on first use. Useful when you need to query or display logs in the admin UI.

Null driver

Silently discards all log entries. Set LOG_DRIVER=null for testing or when you want logging completely off.

Log file security

The .logs/ directory is protected by an .htaccess that denies all HTTP access. Never move the log file outside this directory unless you're confident your server configuration protects it. Log files may contain sensitive data like IPs, emails, and stack traces.

Viewing Logs

# Tail the live log (Lando / SSH)
tail -f .logs/reports.log

# Search for errors
grep '"level":"error"' .logs/reports.log | tail -50

# Last 100 lines
tail -100 .logs/reports.log
Structured context

Always pass a context array as the second argument when the event has relevant data. This makes debugging much faster — you can grep for a specific order ID or user ID across thousands of log lines.
